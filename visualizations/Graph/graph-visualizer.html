Read me first — the one mental model (2 minutes)

Every graph traversal is ONE loop. Take a node out of a bag, mark it, put its neighbours in the bag. That's it. BFS, DFS, Dijkstra, A* and even Prim's MST are all this same loop — what changes is which container the bag is, and therefore which node comes out next.

The universal template

def traverse(adj, start):
    frontier = Container([start])      # ① deque | stack | heap
    seen = set()
    while frontier:
        node = frontier.pop()          #    popleft | pop | heappop
        if node in seen:               # ③ mark on TAKE — always correct
            continue
        seen.add(node)
        process(node)
        for nxt in neighbours(node):   # ② adj list | grid 4-dirs
            frontier.push(nxt)

This is Jeff Erickson's "whatever-first search" — he calls the container a bag, and notes that a stack is a particular type of bag. Learn this one loop and every tab below is it with one thing swapped.

① The container is the difference

deque.popleft()  → oldest first  → BFS
stack.pop()  → newest first  → DFS
heap.heappop()  → cheapest first  → Dijkstra

Berkeley's CS188 puts the deep version in one line: conceptually every frontier is a priority queue — a stack and a queue are just the two cases where the ordering is so simple you can skip the log n.

But the knob is the container and the key. "Min-heap → Dijkstra" is not quite true, and this trips people up later:

what the bag orders byalgorithm you get
insertion orderBFS (FIFO) / DFS (LIFO)
edge weight w(u,v)Prim — minimum spanning tree
dist[u] + w (cumulative from source)Dijkstra — shortest path
dist[u] + w + h(v)A* — Dijkstra biased toward the goal

So the real knob is (container, key, when-you-finalise). Set A*'s heuristic to 0 and it collapses to Dijkstra; make every weight 1 and Dijkstra collapses to BFS. It's one ladder, not five algorithms.

The analogy

You're searching a building. BFS = a crowd steps forward one room at a time — a ripple spreading out evenly. DFS = one scout sprints down a corridor as far as it goes, then backs up and tries the next turn. Same rulebook, different waiting room. The scout is the one you already met in the backtracking visualizer — recursive DFS is this loop with the call stack as the container: every call pushes a frame, every return pops one.

That's the whole mental model. Knob ② (neighbours() — the only per-problem code) and knob ③ (when you mark) you'll meet live in the tabs — flip the mode chips and watch what each choice does.     ③ When do you mark — and why does it depend on the container? after the BFS + DFS chips
    

      

        The rule that never becomes wrong: finalising a node when you REMOVE it from the frontier is always correct. Finalising it when you INSERT it is an optimisation — valid only when insertion order already equals final order.
      

      
Unit weights (BFS) satisfy that condition. Weighted edges (Dijkstra) do not. Everything else follows:

      

        
containerfinalise whenwhy

        

          queue → BFS
          push safe shortcut
          The queue only ever holds two adjacent distance values, in nondecreasing order (CLRS Lemma 22.3) — so the first time you reach a vertex you reached it optimally. Marking at push caps the queue at Θ(V), each vertex enqueued exactly once.
        

        

          stack → DFS
          pop required
          Marking on push still visits every reachable vertex, but the result is not a depth-first search — a node high in the tree claims neighbours as children too early. Cost of doing it right: duplicates on the stack.
        

        

          heap → Dijkstra
          pop required
          A tentative distance can still improve while the node sits in the heap, so marking at push would freeze a non-final answer. Lazy Dijkstra deliberately pushes duplicates and skips stale ones on extraction.
        

      

      
⚠ And here's where almost every interview-prep source gets it wrong. You'll be told "marking on dequeue gives wrong BFS distances." That's false. Mark-on-pop BFS is correct and still O(V+E) — each vertex expands at most once, so pushes stay bounded by 2E. What it actually costs is space: Θ(E) instead of Θ(V).

      
The bug people are really describing is a different one that happens to co-occur: writing dist[v] = dist[u] + 1 at push time, unguarded, so a later longer push overwrites a shorter distance. On the graph above, that bug reports C at distance 2 when it's really 1. Learn it as where you WRITE the distance, not where you mark. The BFS tab's third chip is exactly this bug — watch it happen.

      
The ordering detail: iterative DFS reproduces recursive DFS's visit order only if you push neighbours in reversed order. Push D, C, B so that B pops first. Without the reversal you still get a valid DFS — just a mirrored one.

    

  


  

    Why does BFS give shortest paths — and DFS doesn't? after the BFS tab
    

      
The queue is always sorted by nondecreasing distance, and its largest and smallest values differ by at most 1 — you only ever append d+1 while popping d, so the invariant survives every iteration. Therefore BFS dequeues vertices in nondecreasing order of distance, and every vertex at distance k is discovered before any vertex at distance k+1 is expanded. The first time you touch a vertex, you touched it from the closest shell that reaches it — so that distance is optimal.

      
BFS sweeps outward in complete shells, and the queue is the boundary between the finished shell and the next one. Note the real precondition is unit edge weights, not "unweighted" — a graph where every edge costs 7 is fine too (you just get 7·δ). The moment weights differ, the shell structure breaks and you need the heap.

    

  


  

    Where does the one-loop model genuinely break? worth knowing now
    

      

        
The bag loop gives you preorder only. When you pop v you push all its neighbours and never come back to v — so there is no notion of "finished with v." No finish times, no low-link values, no postorder.

        
That means you cannot get topological-sort-by-finish-time, Tarjan's SCC, or back-edge cycle detection out of the plain loop. Those need three states — New / Active / Done — not one mark bit, and iterating them needs a two-phase stack (push (v, ENTER) / (v, EXIT)), at which point it honestly isn't the same while-loop any more. Course Schedule (LC 207) is the counterexample to everything on this page, and that's fine — knowing where a model stops is part of owning it.

      

    

  


  

    What does it cost — and when does recursion blow the stack? after the DFS recursive chip
    

      
Each vertex is marked at most once, so the neighbour loop runs at most V times. Each undirected edge uv enters the bag exactly twice — once as (u,v), once as (v,u) — so the push line runs at most 2E times. That's where "twice for undirected" actually comes from.

      
    
        
  • Adjacency list: O(V + E) for both BFS and DFS — and O(E) for a connected graph, since V ≤ E+1.
    • 
        
  • Adjacency matrix: listing one vertex's neighbours costs O(V) no matter its degree → O(V²) even on a sparse graph. You cannot recover O(V+E). Space Θ(V²) vs Θ(V+E).
    • 
        
  • Grids are implicit graphs — neighbours are computed, never stored. V = mn, E ≈ 2mn, so O(mn).
    • 
        
  • Space differs, and it decides which one breaks: BFS is O(w), the widest frontier; DFS is O(h), the deepest path. A wide graph blows up BFS; a deep chain blows up DFS.
    • 
      

      
Recursion depth — the real numbers

      
Python's default recursion limit is 1000 (usable depth ~997). Number of Islands allows a 300×300 grid = 90,000 cells, and a recursive flood fill on all-land hits depth 90,000 — 90× over the limit. That's a guaranteed RecursionError, not a theoretical worry.

      
But don't repeat the folklore that raising the limit segfaults: that was true through Python 3.11, and 3.12 changed the model so the limit applies only to Python-level frames (200,000 deep runs fine on 3.13). It's version- and platform-dependent — and since you don't control the judge's version, that uncertainty is itself the argument. It isn't Python-only either: the JVM's default thread stack is roughly 10–20k frames.

      
The honest recommendation: default to iterative BFS on grids. Not because recursion is broken, but because BFS's queue only ever holds the frontier — O(min(m,n)) — while iterative DFS with mark-on-pop can hold Θ(E). It's the only version whose memory you can reason about without knowing the judge's language version.

Write the universal traversal loop from memory — all 3 knobs.

    
frontier = Container([start]) · seen = set() · while frontier: pop → if seen, skip → mark → for each neighbour: push. The knobs: ① which container, ② neighbours(), ③ when you mark. If your version marked at push unconditionally — that's only safe for BFS.


  
What container — and keyed by what — gives you Dijkstra? Prim? A*?

    
All three are a min-heap; the key is the real knob. Keyed by edge weight w(u,v) → Prim. Keyed by dist[u] + w (cumulative from source) → Dijkstra. Keyed by dist[u] + w + h(v) → A*. Set h = 0 and A* collapses to Dijkstra; make every weight 1 and Dijkstra collapses to BFS.


  
When is mark-on-push safe, and what's the one rule that never becomes wrong?

    
Finalise on REMOVE is always correct. Finalising on insert is an optimisation, valid only when insertion order = final order — true for BFS (unit weights), false for DFS (wrong tree) and Dijkstra (freezes a non-final distance).


  
"Marking on dequeue gives wrong BFS distances." True or false — and what's the real bug?

    
False. Mark-on-pop BFS is correct, still O(V+E); it costs Θ(E) space instead of Θ(V). The real bug is writing dist[v] = dist[u]+1 at push time, unguarded, letting a longer path overwrite a shorter one. It's about where you write, not where you mark.


  
Why does BFS give shortest paths, in one sentence?

    
The queue is always sorted by nondecreasing distance (you only append d+1 while popping d), so the first time you reach a vertex you reached it from the closest shell — discovery order = distance order.


  
Name one problem the bag loop cannot solve, and why.

    
Course Schedule (LC 207) — cycle detection by finish times. The bag loop is preorder-only: once you pop v you never come back, so there's no "finished with v", no postorder, no low-links. You need New/Active/Done and a two-phase stack — a genuinely different loop.


  
One note on honesty: every empirical claim on this page — the mark-on-push DFS tree being wrong, mark-on-pop BFS distances being right, the unguarded-distance bug — was verified against reference implementations on the exact graph in the tabs above, not taken from a blog post.
