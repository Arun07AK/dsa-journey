Find Minimum in Rotated Sorted Array

Binary search in O(log n) — at every step throw away the half that can't contain the minimum, and keep the half that must.

1The intuition first — what does "rotated" even look like?

A sorted array [1,2,3,4,5,6] rotated some number of times becomes two sorted runs joined back-to-back, like [4,5,6,1,2,3]. Picture an odometer that rolled past its max and wrapped around: it keeps climbing, then suddenly drops off a cliff back to the lowest number — and that cliff is the minimum.

The whole strategy in one line: compare the middle to the right edge nums[r] — that one comparison tells you which run m sits on, and the minimum is always on the smaller run.

If nums[m] < nums[r], then m is on the smaller run (at or past the cliff). The minimum is at m or to its left → keep m as a candidate, r = m.
Otherwise m is on the larger run (before the cliff). Everything from l..m is above the cliff → the minimum is strictly to the right, l = m+1.

Either way you throw away a whole half — and the comparison is always made against the right edge, because that anchor reliably tells you which side of the cliff m is on.

2Watch it converge — and why shrinking finds the answer

Why does throwing half away land you on the minimum? Think of Guess Who?. You never point at one face and ask "is it this one?" — you ask questions that flip down whole rows you've ruled out. The last face standing wins by elimination.

This search works the same way. Each step deletes a half only after proving every cell in it is bigger than something else — so it can't be the minimum. The half you keep is guaranteed to still contain the min. That's the promise the loop never breaks: the minimum is always inside [l, r]. Shrink that window enough and it collapses to one cell — and that lone survivor is the answer. You didn't test it. You cornered it. Watch the ✗ ruled out tags below — that's elimination happening.

3Why compare to nums[r] — and not nums[l]?

The whole algorithm rests on the comparison nums[m] < nums[r]. Here's both branches laid bare:

✓ nums[m] < nums[r] → go left

m is on the smaller run (at or past the cliff). The minimum is at m or to its left.

So r = m — we keep m because it might be the answer. Never r = m-1, or you could skip over the true minimum.

✗ nums[m] ≥ nums[r] → go right

m is on the larger run (before the cliff). Everything from l..m is bigger than nums[r].

So l = m+1 — the minimum is strictly to the right, and m itself can't be it.

Why nums[r] and not nums[l]? The right edge is a reliable anchor. If you compared against nums[l] instead, a fully-sorted (or fully-rotated) array like [1,2,3,4] breaks the logic — nums[m] > nums[l] is true even though the minimum is at l. Comparing to the right edge handles the not-rotated case for free: nums[m] < nums[r] is always true, so it keeps walking left until l == r == 0.

4The code — and why the loop is while l < r

def findMin(nums):
    l, r = 0, len(nums) - 1
    while l < r:                  # strictly < : stop when the window is one cell
        m = l + (r - l) // 2      # overflow-safe midpoint
        if nums[m] < nums[r]:       # m on the smaller run → min at m or left
            r = m                  # keep m as a candidate
        else:                      # m on the larger run → min strictly right
            l = m + 1
    return nums[l]                # l == r → the minimum
Why l < r here, but l <= h in Search? Different goals → different boundaries. Find-Min shrinks a window toward a single guaranteed survivor — the minimum is always in the window, so the moment l == r the one remaining cell is the answer; stop and return it. Search might find nothing (the target can be absent), so it keeps going until the window is genuinely empty (l > h) before giving up with -1. Here, using <= with r = m would also loop forever when l == r == m — another reason the strict < is right.

5Check yourself — recall before you reveal

Answer in your head (or on paper) first. No scores here — just reveal and compare.

Q1. For [5,6,7,8,1,2,3] (indices 0–6): what are l, m, r right after the first iteration of the loop?
Start: l=0, r=6. m = 0 + (6-0)//2 = 3, so nums[3]=8. Compare 8 < nums[6]=3? → No → go right → l = m+1 = 4.
After iteration 1: l=4, r=6 (m was 3). The window has collapsed to the smaller run [1,2,3] in one step.
Q2. Why is it r = m and not r = m - 1 in the "go left" branch?
Because when nums[m] < nums[r], m itself might be the minimum — it's the smallest element we've seen so far on the smaller run. Discarding it with m-1 could throw away the true answer. We only ever discard the right half (which we've proven is larger) by moving r down to m.
Q3. What's the loop invariant that guarantees the minimum never leaves the window [l, r]?
The minimum is always within [l, r]. Each branch only discards elements proven to be not the minimum: "go right" drops l..m because all of them exceed nums[r]; "go left" drops m+1..r while keeping m as a live candidate. The window shrinks by ~half each step but never excludes the true min → it lands exactly on it when l == r.
Q4. The array [11,13,15,17] was "rotated n times" (i.e. back to sorted). Does this code still return the right answer, and what does it do?
Yes — returns 11. Since the array is fully sorted, nums[m] < nums[r] is true at every step, so it always goes left (r = m), walking the window down to l == r == 0. This is exactly why we anchor on nums[r]: the not-rotated case is handled with zero special-casing.

What you just watched

  • A rotated sorted array is two sorted runs with one cliff — the minimum is the bottom of that cliff.
  • Compare the middle to the right edge nums[r]: smaller → min is at/left of m (r=m); not smaller → min is strictly right (l=m+1).
  • r = m, never r = m-1 — m might be the answer.
  • while l < r (strict), and the answer is nums[l] when the window collapses to one cell.
  • O(log n) time, O(1) space — and the not-rotated array works for free.
