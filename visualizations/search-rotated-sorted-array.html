Search in Rotated Sorted Array

Find a target's index in O(log n) — at each step, figure out which half is sorted, then check if the target lives inside it.

1The intuition — one half is always sorted

A rotated sorted array is two ascending runs joined at a cliff, like [4,5,6,7,0,1,2]. Cut it anywhere with a midpoint mid and here's the magic: at least one of the two halves [l..mid] or [mid..h] is fully sorted — the cliff can only sit in one of them.

The whole strategy in one line: identify the sorted half, then ask "is the target inside its range?"

If nums[mid] >= nums[l], the left half is sorted. Is the target between nums[l] and nums[mid]? If yes, search left; if no, the target must be in the messy right half, so search right.
Otherwise the right half is sorted. Is the target between nums[mid] and nums[h]? If yes, search right; if no, search left.

Either way you throw away a whole half — but the deciding question is always asked against the sorted half, because only there can you reason cleanly about whether the target fits.

2Watch it search — which half is sorted, is the target in it?

Why does narrowing find (or rule out) the target? Same elimination idea as binary search, with one twist: you can't just compare target to nums[mid] (the array isn't globally sorted). So each step first finds the sorted half (the side without the cliff), where order is trustworthy. In that half you can say for sure whether the target's value fits inside the range. If it fits, the target — if it exists at all — is in there; otherwise it's in the other half. Every step deletes one half for a proven reason, so the window shrinks to nothing (target absent → -1) or lands on the target. Watch the blue sorted-half shading flip sides as the window moves.

3The four-way decision, unpacked

Two questions nested: which half is sorted? then is the target in that sorted half's range? That gives four leaves:

Left half sorted — nums[mid] ≥ nums[l]

Target in [nums[l], nums[mid]): search left → h = mid-1.

Otherwise: target is in the unsorted right side → search right → l = mid+1.

Right half sorted — nums[mid] < nums[l]

Target in (nums[mid], nums[h]]: search right → l = mid+1.

Otherwise: target is in the unsorted left side → search left → h = mid-1.

Why nums[mid] >= nums[l] (with the =)? When the window shrinks to one element, mid == l, so nums[mid] == nums[l]. The >= correctly treats that single-element window as a "sorted left half" instead of falling into the right-half branch and mis-reading the bounds. (With all-unique elements this is the only time they're equal.)

4The code — yours, annotated

def search(nums, target):
    l, h = 0, len(nums) - 1
    while l <= h:                       # <= : a 1-cell window can still be the target
        mid = (l + h) // 2
        if nums[mid] == target:
            return mid                   # direct hit
        if nums[mid] >= nums[l]:           # LEFT half is sorted
            if target > nums[mid] or target < nums[l]:
                l = mid + 1            # target not in sorted left → go right
            else:
                h = mid - 1            # target is in sorted left → go left
        else:                            # RIGHT half is sorted
            if target < nums[mid] or target > nums[h]:
                h = mid - 1            # target not in sorted right → go left
            else:
                l = mid + 1            # target is in sorted right → go right
    return -1                          # window emptied → not present
Why l <= h here, but l < r in Find-Min? Find-Min shrinks a window to a single guaranteed survivor — the answer is always there, so it stops at width 1. Search might find nothing: the target may be absent. So it must keep checking until the window is genuinely empty (l > h), and only then return -1. Different goal → different boundary.

5Check yourself — recall before you reveal

Answer in your head (or on paper) first. No scores here — just reveal and compare.

Q1. For [4,5,6,7,0,1,2], target 0: at the first step, which half is sorted, and which way do you go?
l=0, h=6, mid=3 → nums[3]=7. Is nums[mid]=7 ≥ nums[l]=4? Yes → left half [4,5,6,7] is sorted. Is target 0 in [4,7]? No (0 < 4) → go right, l = 4. The whole sorted left half is eliminated in one step.
Q2. Why can't you just compare target directly to nums[mid] like in a normal binary search?
Because the array isn't globally sorted — there's a cliff somewhere. target > nums[mid] doesn't reliably mean "go right," since the larger values might be wrapped around to the left of mid. So you first isolate the sorted half (the side without the cliff), where comparisons are trustworthy, and reason about the range there.
Q3. For [3,4,5,6,1,2], target 9 (absent): what does the function return, and roughly how does the window die?
Returns -1. Each step still eliminates a proven half, but no cell ever equals 9, so the window keeps shrinking until l > h (empty). The while l <= h guard then fails and it returns -1. Absence is detected by the window emptying, not by any special case.
Q4. What's the role of the = in nums[mid] >= nums[l]?
It handles the moment the window is a single element (l == h == mid), where nums[mid] == nums[l]. The = sends that case into the "left half sorted" branch, where the bounds check nums[l]..nums[mid] is just the one element — correct. Drop the = and that single-cell case falls into the right-half branch with a malformed range.

What you just watched

  • A rotated array always has at least one fully-sorted half at any midpoint — the cliff sits in the other half.
  • Find the sorted half (nums[mid] >= nums[l] → left sorted, else right sorted), then ask if the target's value fits inside that half's range.
  • Fits → search that half; doesn't fit → search the other half. Either way one half is eliminated for a proven reason.
  • while l <= h (not <) — the target can be absent, so search until the window is empty, then return -1.
  • O(log n) time, O(1) space. Sibling of Find Minimum — same rotated-array trick, different question.
